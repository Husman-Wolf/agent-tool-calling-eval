# AI Agent 工具调用测试（Tool-Calling Eval）

用 pytest 给一个"会自己调工具"的客服 Agent 写测试集：60 条用例、5 类场景、自动出通过率与失败归因。

> 背景：传统接口测试断言 `code == 200` 就够了，但 Agent 的输入是人话、输出不唯一，
> 真正要判的是 **选没选对工具 / 参数对不对 / 该追问时有没有瞎猜 / 工具报错有没有兜底**。
> 这个仓库就是把这四件事变成可重复执行的用例。

## 结果

| 版本 | 改了什么 | 通过率 |
|---|---|---|
| v1 | 首轮跑通（用例未经校准） | 44 / 60 = **73.3%** |
| v2 | 校准 10 条过度约束用例 + 修断言的参数合并 bug | 51 / 60 = **85.0%** |
| v3 | 修 `cancel_order` 业务漏洞 + 加 system prompt（11 条规则） | 58 / 60 = **96.7%** |

分类通过率（v3）：

| 场景 | 通过 |
|---|---|
| 应调工具 | 15 / 15 |
| 不应调工具 | 10 / 10 |
| 参数缺失 / 歧义 | 11 / 12 |
| 多轮上下文 | 9 / 10 |
| 异常兜底 | 13 / 13 |

失败归因（v3）：工具选错 1 条、参数错误 1 条。

| 文件 | 作用 |

| `agent.py` | 被测对象：客服 Agent（3 个工具 + system prompt） |
| `cases.csv` | 60 条用例，一条一行 |
| `checks.py` | 断言逻辑，pytest 与评测脚本共用 |

## 快速开始

```powershell
pip install openai pytest

# key 单独放一个文件，避免误提交
"sk-你的key" | Out-File -Encoding utf8 key.txt

python run_eval.py          # 跑全量，出通过率 + report.md
pytest -v                   # 按用例看每条的红绿
pytest -v -k 参数缺失        # 只跑某一类
```

## 用例长什么样

`cases.csv` 九列，`||` 表示分多轮说，`|` 表示"任意一个命中即算过"：

```csv
id,category,input,expect_tools,expect_args,expect_no_tools,contains,not_contains,note
A01,应调工具,帮我查下 A1001 的订单状态,get_order_status,order_id=A1001,0,,,正常查询
C06,参数缺失,退一下 A1001,,,0,金额|多少钱|退多少,,缺金额应追问而不要填默认值
D06,多轮上下文,A1001||退款||100,refund,order_id=A1001;amount=100,0,,,第三轮明确说了 100
```

判定规则：

1. `expect_tools` 里的工具必须都被调用过
2. `expect_args` 要求**某一次调用**同时满足全部 `k=v`（不能把多次调用的参数合并来比）
3. `expect_no_tools=1` 时不允许有任何工具调用
4. `contains` / `not_contains` 做关键信息与幻觉的粗筛

## 测出来的 5 个问题

| # | 现象 | 性质 |
|---|---|---|
| 1 | 用户只说"退一下 A1001"（没给金额）时，模型把 `amount` 填 **0** 去调工具，而不是追问 | 参数幻觉 |
| 2 | 用户明确说"退 100"，模型按订单全额 129 退 | **指令优先级被覆盖** |
| 3 | "把 A1001 和 A1002 都退了" → 查了两个订单，一个都没退 | 多任务编排断链 |
| 4 | 已签收的订单调用 `cancel_order` 成功 | 后端业务校验漏洞（非模型问题） |
| 5 | 工具只返回 `{"ok": true}`，模型自己补出"1–3 个工作日到账" | 幻觉，且不易察觉 |

问题 2、3 在 v3 加提示词后仍未完全解决，属于模型能力边界，需要在代码层强制
（例如退款金额必须来自用户原话，不允许模型算术推导）。

## 一个反直觉的规律

| 用户给了什么 | 模型行为 |
|---|---|
| 什么都不给（"帮我退款"） | 追问订单号 + 金额 ✅ |
| 给了订单号、没给金额（"退一下 A1001"） | 金额填 0，直接调工具 ⚠️ |

**信息全缺时会问，缺一部分时反而会瞎填。** 所以用例必须按"参数缺失程度"分维度覆盖，
不能只测"全给"和"全不给"两种情况。

## 方法论上的两个坑

**1. 关键词断言不可靠。**
v1 有 5 条失败是纯措辞问题（模型说"系统中没有该订单号"，断言写的是"查不到"）。
自然语言有无数种说法，`contains` 永远写不全 —— 生产环境应改用 rubric + 三态判定
（通过 / 不通过 / 不可判分），或 LLM-as-judge。

**2. 提示词会让模型"对齐到评测集"。**
v3 里那 5 条措辞类失败之所以通过，一部分原因是 system prompt 要求"如实转述 error 原因"，
模型于是用了"查不到订单""无法取消"——正好是断言里的关键词。
真实用户不会照着关键词说话，所以通过率不能只用关键词断言来证明质量。

## 局限

- 只测了 `deepseek-chat` 一个模型，未做多模型对比
- 单次运行有随机性，同一用例多次跑结果可能不同；严格评测应重复 N 次取通过率均值
- 60 条是人工构造的，规模小；未覆盖工具超时、并发、脏数据等场景
- 断言以规则为主，未引入 LLM 判定
